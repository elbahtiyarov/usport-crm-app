# USPORT CRM

Каталог товаров, клиенты, конвейер заказов (по принципу автомойки — заказ
проходит через фиксированные посты по очереди: Заявка → Расчёт → КП →
Согласование → Оплата → Производство → Отгрузка) и генератор документов
(КП / Счёт / Накладная / Договор) с логотипом и реквизитами компании.

Node.js + Express + PostgreSQL, один статичный `public/index.html` в
качестве интерфейса — без сборки и фреймворков на фронте.

```

├── server/

│   ├── db.js             # пул подключений к Postgres
│   ├── uploads/          # сюда сохраняется загруженный логотип

│       ├── orders.js

├── docker-compose.yml     # сервисы db (Postgres) + app (сам сервер)
├── Dockerfile
├── package.json

```

## Запуск через Docker (рекомендуется)

```bash
# 1. Собрать и поднять оба сервиса (Postgres + приложение)
docker compose up -d --build

# 2. Применить схему базы данных (один раз)
docker compose exec app npm run migrate
```

Открыть в браузере: **http://localhost:3000**

Логи: `docker compose logs -f app`
Остановить: `docker compose down` (данные в volume `usport_db_data` сохранятся)

## Запуск без Docker

Нужен установленный Node.js 18+ и PostgreSQL 14+.

```bash
# 1. Создать базу
psql -U postgres -c "CREATE DATABASE usport_crm;"

# 2. Отредактировать .env — указать локальную строку подключения, например:
#    DATABASE_URL=postgresql://usport:usport@localhost:5432/usport_crm

# 3. Установить зависимости и применить схему
npm install
npm run migrate

# 4. Запустить сервер
npm start
```

## Авторизация (логин + пароль, без отправки почты)

Вход простой: логин (любая строка, необязательно похожая на email) +
пароль. **Первый вход с новым логином — это и есть регистрация**: какой
пароль введёте, такой и запомнится. При следующих входах он уже
проверяется как обычно. Сессия хранится в httpOnly-cookie на 30 дней.

Настройки — в `.env` (переменные называются `*_EMAILS` по историческим
причинам, но туда можно вписывать любые логины, не только похожие на
email):

- `JWT_SECRET` — обязательно замените на свою случайную строку
  (`openssl rand -hex 32`), иначе чужие сессии можно подделать.
- `ALLOWED_EMAILS` — список логинов через запятую, кому вообще разрешён
  вход/регистрация. Пусто = зарегистрироваться сможет кто угодно
  (годится только для теста).
- `ADMIN_EMAILS` — список логинов через запятую, кто получает роль
  **admin** (видит и может редактировать/удалять любые записи, не
  только свои). Всех остальных — роль **manager**, у них доступ к
  чужим клиентам/заказам/документам только на просмотр.

Роль admin выдаётся автоматически при входе, если логин есть в списке —
менять её вручную в базе не нужно, достаточно вписать логин в `.env` и
перезапустить сервер.

Выйти можно кнопкой со стрелкой в правом верхнем углу или в самом низу
сайдбара.

Настройки `GMAIL_*`/`YANDEX_*`/`MAILRU_*`/`SMTP_*` в `.env` сейчас ничего
не делают — оставлены на случай, если позже понадобится вернуть
подтверждение по коду на почту.

## Таблицы базы данных

- `products` — каталог: артикул, наименование, категория, цена, характеристики
- `clients` — клиенты: контакты, источник обращения, реквизиты, заметки
- `orders` + `order_items` — заказы и их состав; `orders.stage` хранит текущий
  этап конвейера
- `documents` + `document_items` — КП, счета, накладные и договоры;
  `documents.doc_type` отличает тип документа
- `settings` — единственная строка с реквизитами и логотипом компании
- `users` — те, кто хоть раз входил (аккаунт создаётся при первом входе с новым email), хранит хеш пароля
- `auth_codes` — не используется при входе по паролю; оставлена в схеме на случай возврата входа по коду на почту

Полная схема — в `db/schema.sql`.

## Логотип компании

Загружается на вкладке «Настройки», сохраняется на диске сервера в
`server/uploads/` (в Docker — в volume `usport_uploads`, переживает
пересоздание контейнера) и отдаётся статикой по `/uploads/<файл>`.

## Печать документов (КП, счёт, накладная, договор)

Кнопка «Печать» открывает системный диалог печати браузера — там же есть
«Сохранить как PDF».

## Права доступа: свои vs чужие записи

Клиентов, заказы и документы видят все, кто вошёл, но **редактировать и
удалять может только тот, кто создал запись** (в интерфейсе у чужих
записей кнопки «Изменить»/«Удалить» просто не показываются, вместо них —
«только просмотр»; сервер тоже это проверяет, а не только фронтенд).

Роль **admin** (задаётся через `ADMIN_EMAILS` в `.env`, через запятую)
видит и может редактировать/удалять **любые** записи — например, если
менеджер уволился, а его клиентов нужно передать другому.

Записи, созданные до включения этой функции (`created_by` пустой),
остаются доступны всем — ничего не заблокируется задним числом.

Каталог товаров (`products`) и настройки компании (`settings`) — общие
для всей команды, ограничение на них не действует.

## Фото товара

В карточке товара можно (необязательно) загрузить фото — сохраняется в
`server/uploads/`, как и логотип компании. Без фото товар тоже прекрасно
сохраняется, в таблице на его месте просто пустая рамка.

Если позицию в заказ или документ (КП/счёт/накладную) добавили **из
каталога** (а не вручную), фото товара переносится вместе с ней и
попадает в напечатанный документ отдельной колонкой — колонка появляется,
только если хотя бы у одной позиции есть фото.

## Импорт из Excel

На вкладке **«Товары»** кнопка «Импорт прайса из Excel» берёт `.xlsx`-файл,
находит в нём лист с колонками «Артикул» и «Наименование» (заголовки
ищутся по смыслу, а не по номеру ячейки — колонки можно переставлять) и:
- если товар с таким артикулом уже есть — обновляет название, цену и характеристики;
- если нет — добавляет новый.
Также забирает «Ед. изм.», «Вес», «Объём» (складывает в характеристики) и
колонку «Цена» — **проверьте, что это цена для клиента, а не закупочная/дилерская**,
прежде чем пускать такой прайс в дело.

На вкладке **«Документы»** кнопка «Импорт КП из Excel» ищет на листах
файла текст «КОММЕРЧЕСКОЕ ПРЕДЛОЖЕНИЕ» и таблицу позиций рядом с ним
(колонки «Артикул», «Наименование», «Кол-во», «Цена»/«Цена со скидкой»).
На каждое найденное предложение создаётся черновик документа-КП с этими
позициями, суммой и клиентом (берётся из строки «Кому:»); сам файл при
этом не изменяется. Дальше документ можно открыть, поправить и распечатать
как обычно.

## Деплой на Railway (чтобы показать в интернете)

У проекта уже есть `Dockerfile` — Railway соберёт его автоматически,
дополнительно ничего писать не нужно.

1. Залейте проект на GitHub (см. раздел про git выше, если ещё не сделали).
2. На [railway.app](https://railway.app) — **New Project → Deploy from GitHub repo**,
   выберите этот репозиторий.
3. В том же проекте — **+ New → Database → Add PostgreSQL**. Railway сам
   создаст базу и положит переменную `DATABASE_URL` — вручную вводить
   строку подключения не нужно, Railway сам подставит её в переменные
   окружения вашего сервиса (Variables → Add Reference → выбрать
   `DATABASE_URL` из сервиса Postgres).
4. В **Variables** вашего сервиса (не базы) добавьте:
   ```
   JWT_SECRET=<случайная строка>
   ALLOWED_EMAILS=ваша_почта@example.com
   ADMIN_EMAILS=ваша_почта@example.com
   ```
   `PORT` задавать не нужно — Railway подставляет его сам, сервер уже
   читает `process.env.PORT`.
5. Примените схему БД один раз — из Railway CLI (`railway run npm run migrate`,
   предварительно `railway link` к проекту) либо через вкладку **Deploy →
   Shell/Command** сервиса, если она доступна в вашем плане.
6. После деплоя Railway выдаст публичный адрес вида
   `https://<проект>.up.railway.app` — это и есть ссылка для показа в интернете.

**Фото и логотип не переживут передеплой без диска.** Railway пересоздаёт
контейнер при каждом деплое, а `server/uploads/` внутри контейнера —
временная папка. Чтобы загруженные фото и логотип сохранялись, добавьте
Railway **Volume** и примонтируйте его на `/app/server/uploads`
(Settings сервиса → Volumes → Add Volume, mount path именно такой, раз
Dockerfile кладёт код в `/app`).

Если подключение к базе падает с ошибкой про SSL — добавьте переменную
`DATABASE_SSL=true` (обычно не нужно, если сервис и база в одном
Railway-проекте на одной приватной сети).
