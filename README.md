# USPORT CRM

Каталог товаров, клиенты, конвейер заказов (по принципу автомойки — заказ
проходит через фиксированные посты по очереди: Заявка → Расчёт → КП →
Согласование → Оплата → Производство → Отгрузка → Завершён) и генератор
документов
(КП / Счёт / Накладная / Договор) с логотипом и реквизитами компании.

Node.js + Express + PostgreSQL, один статичный `public/index.html` в
качестве интерфейса — без сборки и фреймворков на фронте.


## Запуск через Docker (рекомендуется)

```bash
docker compose up -d --build
```

Схема базы данных применяется автоматически при старте контейнера
(`db/migrate.js` выполняется перед запуском сервера) — отдельно
накатывать её не нужно.

Открыть в браузере: **http://localhost:3000**

Логи: `docker compose logs -f app`
Остановить: `docker compose down` (данные в volume `usport_db_data` сохранятся)

## Запуск без Docker

Нужен установленный Node.js 18+ и PostgreSQL 14+.

```bash
# 1. Создать базу
psql -U postgres -c "CREATE DATABASE usport_crm;"

# 2. Отредактировать .env — указать локальную строку подключения, например:
#    DATABASE_URL=postgresql://usport:usport@localhost:5432/usport_crm

# 3. Установить зависимости и применить схему
npm install
npm run migrate

# 4. Запустить сервер
npm start
```

## Авторизация (логин + пароль, без отправки почты)

Вход простой: логин (любая строка, необязательно похожая на email) +
пароль. **Первый вход с новым логином — это и есть регистрация**: какой
пароль введёте, такой и запомнится. При следующих входах он уже
проверяется как обычно. Сессия хранится в httpOnly-cookie на 30 дней.

Настройки — в `.env` (переменные называются `*_EMAILS` по историческим
причинам, но туда можно вписывать любые логины, не только похожие на
email):

- `JWT_SECRET` — обязательно замените на свою случайную строку
  (`openssl rand -hex 32`), иначе чужие сессии можно подделать.
- `ALLOWED_EMAILS` — список логинов через запятую, кому вообще разрешён
  вход/регистрация. Пусто = зарегистрироваться сможет кто угодно
  (годится только для теста).
- `ADMIN_EMAILS` — список логинов через запятую, кто получает роль
  **admin** (видит и может редактировать/удалять любые записи, не
  только свои). Всех остальных — роль **manager**, у них доступ к
  чужим клиентам/заказам/документам только на просмотр.

Роль admin выдаётся автоматически при входе, если логин есть в списке —
менять её вручную в базе не нужно, достаточно вписать логин в `.env` и
перезапустить сервер.

### Раздел «Пользователи» (только для admin)

Помимо самостоятельной регистрации (см. выше), администратор теперь
может сам заводить логины и пароли для менеджеров — не нужно объяснять
человеку, что вход = регистрация, и не нужно вписывать его логин в
`ALLOWED_EMAILS`: если аккаунт уже создан в разделе «Пользователи», он
может войти сразу, `ALLOWED_EMAILS` в этом случае не проверяется (он
ограничивает только самостоятельную регистрацию новых, ещё не
существующих аккаунтов).

В разделе видно: логин, роль, дата создания, дата последнего входа.
Можно:
- **Создать** — задать логин, начальный пароль и роль (менеджер/админ);
  сообщите эти логин и пароль человеку — он входит сразу, ничего
  регистрировать не нужно.
- **Изменить** — сменить роль или сбросить пароль (новый пароль —
  необязательное поле, если оставить пустым, старый пароль сохранится).
- **Удалить** — но не самого себя (администратор не может ни удалить,
  ни понизить в роли собственный аккаунт — это защита от случайной
  потери доступа; если admin всего один, только он должен быть в
  `ADMIN_EMAILS`).

Раздел не виден и недоступен по API пользователям с ролью manager —
и на фронтенде, и на сервере (`requireAdmin`).

Выйти можно кнопкой со стрелкой в правом верхнем углу или в самом низу
сайдбара.

Настройки `GMAIL_*`/`YANDEX_*`/`MAILRU_*`/`SMTP_*` в `.env` сейчас ничего
не делают — оставлены на случай, если позже понадобится вернуть
подтверждение по коду на почту.

## Таблицы базы данных

- `products` — каталог: артикул, наименование, категория, цена, характеристики
- `categories` — список категорий товаров (редактируется в разделе «Категории»)
- `clients` — клиенты: контакты, источник обращения, реквизиты, заметки
- `orders` + `order_items` — заказы и их состав; `orders.stage` хранит текущий
  этап конвейера
- `documents` + `document_items` — КП, счета, накладные и договоры;
  `documents.doc_type` отличает тип документа
- `settings` — единственная строка с реквизитами и логотипом компании
- `users` — те, кто хоть раз входил (аккаунт создаётся при первом входе с новым email), хранит хеш пароля
- `auth_codes` — не используется при входе по паролю; оставлена в схеме на случай возврата входа по коду на почту
- `messages` — личные сообщения между пользователями (текст, вложение, ответ на сообщение, прочитано ли)

Полная схема — в `db/schema.sql`.

## Логотип компании

Загружается на вкладке «Настройки», сохраняется на диске сервера в
`server/uploads/` (в Docker — в volume `usport_uploads`, переживает
пересоздание контейнера) и отдаётся статикой по `/uploads/<файл>`.

## Печать и PDF документов (КП, счёт, накладная, договор)

Два способа получить документ:
- **«Скачать PDF»** — формирует файл прямо на сервере (библиотека
  `pdfkit`) и скачивает его сразу, без диалога печати браузера. Основной
  способ — удобнее всего, особенно на телефоне.
- **«Печать»** — открывает системный диалог печати браузера (там же есть
  «Сохранить как PDF» вручную) — на случай, если нужно сразу отправить
  на физический принтер.

PDF использует шрифт DejaVu Sans (`server/fonts/`, лицензия свободная,
входит в проект) — поддерживает кириллицу и знак ₸. Если у позиций
документа есть фото (добавлены из каталога или пришли из импорта Excel
со встроенными картинками), они попадают и в PDF, с переносом на новую
страницу и таблицей позиций. При большом количестве фото файл PDF может
получиться увесистым (фото встраиваются в исходном разрешении).

## Права доступа: свои vs чужие записи

Товары, клиенты, заказы и документы видят все, кто вошёл, но
**редактировать и удалять может только тот, кто создал запись** (в
интерфейсе у чужих записей кнопки «Изменить»/«Удалить» просто не
показываются, вместо них — «только просмотр»; сервер тоже это проверяет,
а не только фронтенд). В каждой из этих таблиц есть колонка **«Автор»** —
видно, кто добавил запись.

Роль **admin** (задаётся через `ADMIN_EMAILS` в `.env`, через запятую)
видит и может редактировать/удалять **любые** записи — например, если
менеджер уволился, а его клиентов нужно передать другому.

Записи, созданные до включения этой функции (`created_by` пустой),
остаются доступны всем — ничего не заблокируется задним числом.

Настройки компании (`settings`) — общие для всей команды, ограничение на
них не действует.

### Согласование заказа — подтверждает только admin

Обычно менеджер сам двигает свой заказ по всем этапам. Но переход
**с «Согласования» на «Оплату»** — исключение: это может сделать только
пользователь с ролью admin (кнопками ‹ › на карточке заказа или через
форму «Изменить» — проверка на сервере одинаковая для обоих способов).

Пока заказ стоит на «Согласовании», у менеджера вместо стрелки «вперёд»
показывается пометка «Ждёт подтверждения администратора» — сам заказ
при этом по-прежнему можно редактировать (поправить состав, клиента).
У админа вместо обычной стрелки — заметная зелёная кнопка
«✓ Подтвердить». После подтверждения на карточке заказа появляется, кто
и когда его одобрил.

Отправить заказ назад на доработку (с «Согласования» на «КП»/«Расчёт») —
может как обычно и сам менеджер, без участия админа; при повторном
попадании на «Согласование» отметка о прошлом подтверждении сбрасывается
(нужно подтверждать заново).

## Сообщения между пользователями

Раздел **«Сообщения»** — личная переписка между двумя конкретными
людьми, как в обычном мессенджере: слева список собеседников (все
остальные пользователи системы) с превью последнего сообщения и
счётчиком непрочитанных, справа — сама переписка.

Доступно всем, кто вошёл (не только admin) — иначе не с кем общаться.
Обновляется без перезагрузки страницы: пока открыта вкладка «Сообщения»,
список и переписка опрашиваются раз в 4 секунды; бейдж с числом
непрочитанных в сайдбаре обновляется раз в 20 секунд всегда, на любой
вкладке. Это обычный опрос (polling), не WebSocket — для команды из
нескольких человек этого достаточно, а деплой при этом остаётся
простым (не нужен отдельный сервис для сокетов). Фоновое обновление не
трогает поле ввода — раньше это приводило к тому, что фокус слетал
прямо во время набора текста, теперь исправлено.

К сообщению можно прикрепить фото или документ (кнопка со скрепкой, до
10 МБ) — фото показывается прямо в переписке превью, документ — ссылкой
для скачивания.

Рядом — эмодзи (кнопка со смайликом, встроенный набор, без интернета) и
гифки (кнопка с рамкой) — поиск и подборка трендов через Giphy, сервер
прячет ключ и проксирует запрос. Без своего ключа используется общий
демо-ключ Giphy (`GIPHY_API_KEY` в `.env` пуст) — работает сразу, но
может тормозить под нагрузкой, так как он общий на весь интернет;
бесплатный личный ключ — на developers.giphy.com, занимает пару минут.
Гифки не скачиваются на ваш сервер — просто ссылка на CDN Giphy.

На любое сообщение можно ответить (кнопка ↩, появляется при наведении
на сообщение) — как в WhatsApp/Telegram: над полем ввода появляется
цитата, кому и на что отвечаете, с крестиком отмены; в самом сообщении
цитата показывается сверху.

## Вес, объём и несколько видов цены у товара

У товара теперь можно указать (всё необязательно):
- **Вес** (кг) и **объём** (м³) — переносятся в позицию заказа/документа
  при добавлении из каталога. В модалке заказа/КП и в напечатанном
  документе/PDF под «Итого» появляется строка «Габариты: вес … кг ·
  объём … м³» — сумма по всем позициям.
- **Дилерская цена**, **оптовая цена** — вводятся вручную, необязательные.
- **Цена с НДС** — не вводится вручную, а считается сама: укажите
  **ставку НДС в %** (по умолчанию 12 — стандартная ставка в Казахстане),
  и цена с НДС посчитается как `Цена × (1 + НДС/100)`. Прямо в форме
  товара под полем НДС сразу видно получившуюся сумму.
- Все виды цены видны отдельными колонками в таблице «Товары»
  (Дилер/Опт/С НДС), а не только в форме редактирования.

При добавлении товара из каталога в заказ или документ
(КП/счёт/накладная/договор) можно выбрать, какую именно цену
подставить — выпадающий список показывает только те виды цены, что
реально заполнены у товара, с суммой в скобках.

## НДС на весь заказ/документ

Отдельно от цен товара — в модалке заказа и документа (КП/счёт/
накладная/договор) есть галочка **«Учитывать НДС (16%) в итоге»**.
Отмечена — «Итого» считается как сумма позиций × 1.16, и в модалке,
печати и PDF появляется разбивка: «Без НДС: … · НДС 16%: …». Не
отмечена — «Итого» как обычно, без наценки. 16% — актуальная ставка
НДС в Казахстане с 1 января 2026 (новый Налоговый кодекс; раньше было
12%).

Импорт прайса из Excel тоже подхватывает вес/объём (если в файле есть
такие колонки) — раньше они попадали только в текст характеристик,
теперь ещё и в отдельные числовые поля.

В напечатанном КП/счёте/накладной (и в PDF) таблица позиций сама
показывает отдельными колонками все виды цены, что были заполнены у
товара при добавлении (Розница/Дилер/Опт/С НДС) — не только ту, что
выбрали для расчёта суммы. Если у товара была указана только обычная
цена, лишние колонки не показываются — таблица остаётся простой.

## Нумерация документов

Раньше документы отображались как «КП-00006» (сквозной ID в базе).
Теперь — «№6 от 22.09.2026, Асхат»: номер считается отдельно по
каждому типу документа (КП, счета, накладные, договоры нумеруются
независимо друг от друга, каждый начинается с №1), плюс дата создания
и логин того, кто создал. Формат одинаковый в таблице документов, в
предпросмотре печати и в PDF.

## История заказов клиента

В разделе «Клиенты» у каждого — кнопка **«История»**: список всех его
заказов (этап, состав, сумма, дата) и документов (тип, номер, сумма,
статус, дата). Доступно на просмотр всем, кто вошёл, независимо от
того, кто создавал сами заказы/документы — это просто сводка, ничего
не редактирует.

## Категории товаров

Раньше список категорий (Обувь, Одежда, Инвентарь, Аксессуары, Прочее)
был зашит в коде. Теперь это отдельный раздел **«Категории»** — можно
добавлять свои, переименовывать и удалять. При установке в базу
попадают те же пять стартовых категорий (чтобы ничего не потерялось),
дальше — как удобно.

Категория у товара — это просто текст, а не жёсткая связь: если удалить
категорию, у товаров, которые ей пользовались, значение в поле
«Категория» просто останется текстом вне списка (при следующем
редактировании товара оно всё ещё будет видно и выбрано, просто больше
не предлагается в выпадающем списке для новых товаров).

## Фото товара

В карточке товара можно (необязательно) загрузить фото — сохраняется в
`server/uploads/`, как и логотип компании. Без фото товар тоже прекрасно
сохраняется, в таблице на его месте просто пустая рамка.

Если позицию в заказ или документ (КП/счёт/накладную) добавили **из
каталога** (а не вручную), фото товара переносится вместе с ней и
попадает в напечатанный документ отдельной колонкой — колонка появляется,
только если хотя бы у одной позиции есть фото.

## Импорт из Excel

На вкладке **«Товары»** кнопка «Импорт прайса из Excel» берёт `.xlsx`-файл,
находит в нём лист с колонками «Артикул» и «Наименование» (заголовки
ищутся по смыслу, а не по номеру ячейки — колонки можно переставлять) и:
- если товар с таким артикулом уже есть — обновляет название, цену и характеристики;
- если нет — добавляет новый.
Также забирает «Ед. изм.», «Вес», «Объём» (складывает в характеристики) и
колонку «Цена» — **проверьте, что это цена для клиента, а не закупочная/дилерская**,
прежде чем пускать такой прайс в дело.

На вкладке **«Документы»** кнопка «Импорт КП из Excel» ищет на листах
файла текст «КОММЕРЧЕСКОЕ ПРЕДЛОЖЕНИЕ» и таблицу позиций рядом с ним
(колонки «Наименование», «Кол-во», «Цена»/«Цена со скидкой»; колонка с
артикулом необязательна — подходит и «Артикул», и «Код»). На каждое
найденное предложение создаётся черновик документа-КП с этими позициями,
суммой и клиентом (берётся из строки «Кому:»); сам файл при этом не
изменяется. Если в файле встроены картинки товаров (в столбце
«Рисунок»/«Фото») — они сохраняются и попадают в документ.

**Заодно эти же позиции добавляются или обновляются в каталоге товаров**
(«Товары») — по тому же принципу, что и импорт прайса: совпадение по
артикулу/коду, у существующего товара обновляется цена, фото
подставляется, только если его ещё не было (не перезатирает то, что вы
уже загрузили вручную). Итоговое окно покажет отдельно, сколько
документов создано и сколько товаров добавлено/обновлено в каталоге.

Дальше документ можно открыть, поправить и распечатать как обычно.

## Деплой на Railway (чтобы показать в интернете)

У проекта уже есть `Dockerfile` — Railway соберёт его автоматически,
дополнительно ничего писать не нужно.

1. Залейте проект на GitHub (см. раздел про git выше, если ещё не сделали).
2. На [railway.app](https://railway.app) — **New Project → Deploy from GitHub repo**,
   выберите этот репозиторий.
3. В том же проекте — **+ New → Database → Add PostgreSQL**. Railway сам
   создаст базу и положит переменную `DATABASE_URL` — вручную вводить
   строку подключения не нужно, Railway сам подставит её в переменные
   окружения вашего сервиса (Variables → Add Reference → выбрать
   `DATABASE_URL` из сервиса Postgres).
4. В **Variables** вашего сервиса (не базы) добавьте:
   ```
   JWT_SECRET=<случайная строка>
   ALLOWED_EMAILS=ваша_почта@example.com
   ADMIN_EMAILS=ваша_почта@example.com
   ```
   `PORT` задавать не нужно — Railway подставляет его сам, сервер уже
   читает `process.env.PORT`.
5. Схема БД применяется **автоматически** при каждом запуске контейнера
   (Dockerfile сначала выполняет `db/migrate.js`, потом стартует сервер) —
   вручную ничего запускать не нужно. Это безопасно: все команды в
   `db/schema.sql` идемпотентны (`CREATE TABLE IF NOT EXISTS`,
   `ADD COLUMN IF NOT EXISTS`), повторный прогон ничего не портит.
6. После деплоя Railway выдаст публичный адрес вида
   `https://<проект>.up.railway.app` — это и есть ссылка для показа в интернете.

**Если всё же нужно применить миграцию вручную с компьютера**
(`railway run npm run migrate`), учтите: переменная `DATABASE_URL`,
которую даёт Railway, — это **внутренний** адрес вида
`postgres.railway.internal`, он резолвится только изнутри Railway.
`railway run` выполняет команду **на вашем компьютере**, поэтому такой
адрес всегда даст `ENOTFOUND`. Нужно временно подставить публичный адрес
базы (сервис Postgres → Connect → Public Network, обычно
`DATABASE_PUBLIC_URL`) — например, в PowerShell:
```
$env:DATABASE_URL="<публичная строка подключения>"; npm run migrate
```

**Фото и логотип не переживут передеплой без диска.** Railway пересоздаёт
контейнер при каждом деплое, а `server/uploads/` внутри контейнера —
временная папка. Чтобы загруженные фото и логотип сохранялись, добавьте
Railway **Volume** и примонтируйте его на `/app/server/uploads`
(Settings сервиса → Volumes → Add Volume, mount path именно такой, раз
Dockerfile кладёт код в `/app`).

Если подключение к базе падает с ошибкой про SSL — добавьте переменную
`DATABASE_SSL=true` (обычно не нужно, если сервис и база в одном
Railway-проекте на одной приватной сети).
